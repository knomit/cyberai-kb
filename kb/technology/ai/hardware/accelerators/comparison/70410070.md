# Ascend 950's binding inference constraint is memory bandwidth (1.4 TB/s vs B200's 8 TB/s), not software

Huawei's current flagship Ascend 950 (950PR, Da Vinci 3.0) carries 112 GB HiBL memory at 1.4 TB/s, vs Nvidia B200's 192 GB HBM3e at 8.0 TB/s — a 5.7x bandwidth ratio.

WHY THIS IS DECISIVE: LLM decode at small batch sizes is memory-bandwidth-bound, not compute-bound. Each forward pass loads model weights and KV cache from memory; token throughput scales roughly linearly with that load rate. The 5.7x bandwidth ratio therefore maps almost directly onto a ~5.7x decode throughput gap at small batches — the regime that dominates real-time serving. The gap does not close at long context, since KV cache loading also scales with bandwidth. Estimated Llama 3.3 70B FP8 throughput: Ascend 950 ~200 tok/s at batch 1 vs B200 ~1,150; ~730 vs ~3,600 at batch 32.

KEY IMPLICATION: this constraint CANNOT be closed in software. Analyses that name CANN/software maturity as 'the decisive bottleneck' for Ascend inference are pointing at the wrong layer. Software (CANN 8.x, torch_npu, the community vLLM Ascend backend which lags upstream and has incomplete DeepSeek V4 MoE routing support) is a real cost — estimated 2–8 weeks of porting — but it is a fixable engineering cost, whereas HBM-class bandwidth is a hardware and manufacturing constraint.

EVIDENCE QUALITY — read carefully: there is no Western-accessible datasheet for the Ascend 950. All specs are Huawei-claimed figures from Chinese-language announcements plus third-party analysis. The throughput numbers above are bandwidth-scaling PROJECTIONS from H200 baselines, not measured results; at batch 32+ inference shifts toward compute-bound, so actual Ascend throughput could exceed these conservative projections. Huawei FP4 and Nvidia NVFP4 are different formats and their peak TFLOPS are not directly comparable.
