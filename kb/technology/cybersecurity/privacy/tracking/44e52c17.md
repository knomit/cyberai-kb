# GDID mechanism: server-minted MSA Device PUID stamped onto Microsoft first-party telemetry, not network-layer inference

The Windows GDID is transmitted as an explicit identifier field on outbound requests to Microsoft first-party endpoints; it is NOT inferred from network-layer fingerprinting and is NOT visible to third parties. Correct mental model: extraction into Microsoft's own service logs, followed by correlation within Microsoft's data estate.

Provisioning chain (per Zerotrace Labs and the SmtimesIWndr/gdid-reversal reverse-engineering): wlidsvc provisions the device against login.live.com; Microsoft's server assigns a Device PUID; the value is written to the registry; cdp.dll (Connected Devices Platform) reads the PUID via the identity stack and registers it into Microsoft's Device Directory Service as the string form g:<decimal>. Endpoints involved include dds.microsoft.com and activity.windows.com.

Encoding: GDID is a 64-bit MSA Device PUID, not a 128-bit hardware hash (a widely repeated social-media claim that is false). User PUIDs are the 0003 class; device PUIDs are the 0018 class. Example from the complaint: g:6755467234350028 = 0x0018000FC8CB93CC. Readable without admin via PowerShell: (Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\IdentityCRL\ExtendedProperties').LID returns 16 hex digits. The same value appears as DeviceId under HKCU\SOFTWARE\Microsoft\IdentityCRL\Immersive\production\Token\{...}, and under HKLM\SOFTWARE\Microsoft\IdentityStore (DeviceId and LID).

Carrier surfaces: Windows activation, diagnostic/telemetry events, Microsoft Store purchases/licenses/installs, Delivery Optimization (reported as UCDOStatus.GlobalDeviceId in Azure Monitor), push notification channels, clipboard-related services, and Edge enhanced diagnostics (which carries browsing history) when enabled.

Why VPNs do not help: the join key sits above the network layer. A VPN changes the IP column in Microsoft's log rows while the GDID column stays constant, so Microsoft can join across sessions, IPs, and geographies on legal process. This also explains the ngrok signup-page observation in the Stokes complaint — the visit was almost certainly logged by a Microsoft-side service observing third-party browsing (SmartScreen URL reputation or Edge enhanced diagnostics), not reported to Microsoft by ngrok.

Unresolved tension worth tracking: the federal complaint states a Windows reinstall yields a new GDID, but Zerotrace Labs claims Microsoft's server re-links device identity to hardware within a single wlidsvc call and that 'the only real reset is new hardware.' Zerotrace describes four stacked identity layers: (1) plaintext LID as a REG_SZ in HKCU, (2) a DPAPI-wrapped X.509 device certificate with private key, signed by a Microsoft CA, decryptable with admin, (3) hardware descriptors such as SMBIOS UUID, spoofable on a VM, (4) TPM/EK attestation. Both claims can hold simultaneously if the GDID VALUE rotates on reinstall while Microsoft server-side still associates old and new records via hardware/TPM attestation — which would make reinstalling substantially weaker as a privacy measure than the complaint's wording implies. Zerotrace suggests running Windows in a VM as the practical mitigation, since hardware descriptors are spoofable there.

Contested claim, direction of correction: the common advice that a local account prevents GDID assignment appears wrong. The author of the gdid-reversal repo updated it to state that CDP has an anonymous device path used when no Microsoft Account is connected, so a GDID exists regardless — it simply is not bound to an MSA. Microsoft has published no comprehensive technical confirmation of any of these data flows, so all of the above are reported research findings rather than vendor-documented platform behavior.
