# Taint Tracking as Provenance-Based IPI Defense: Context Scanner Architecture

Provenance-based context scanning sidesteps content-inspection limitations by asking 'where did this come from?' rather than 'does this look malicious?' Encoding tricks and classifier evasion are irrelevant — the trust level is determined by source metadata.

**Mechanism (taint tracking applied to LLM context assembly):**
1. Every text segment entering context is tagged with a trust level at ingestion — in a parallel provenance manifest, not in the text itself: SYSTEM / USER / INTERNAL_AGENT / EXTERNAL_EMAIL / EXTERNAL_WEB / TOOL_OUTPUT
2. Before context is sent to model, a scanner processes tainted (EXTERNAL_*) regions and applies policy:
   - **Sanitize**: strip instruction-like patterns while preserving content meaning
   - **Wrap**: enclose in strong delimiters instructing model to treat as raw data only
   - **Block**: reject context if high-confidence injected instructions detected
   - **Audit**: pass through and log for post-hoc review
3. Implemented as an LLM API proxy with a provenance manifest between application and model endpoint

**Why it stops EchoLeak class of attacks:** Injected instruction was in an inbound email — EXTERNAL_EMAIL provenance. Scanner wraps it. Encoding techniques used to evade Microsoft's XPIA are irrelevant — trust level comes from source metadata.

**Hard open problems:**
- Taint propagation after summarization: laundering taint via agent summarization is a real attack path
- Scanner's own attack surface: an LLM-based scanner is itself susceptible to injection from the content it reads
- Utility destruction: aggressive sanitization breaks tasks that require processing external content
- Instrumentation gap: requires every tool call and retrieval step to emit provenance metadata — needs SDK adoption across LangGraph, AutoGen, CrewAI etc.
