# A leaked GitLab incoming-issue-email address lets an attacker push code and run CI jobs as the victim

GitLab's incoming-email feature issues each user a non-expiring, per-user email token for filing issues and merge requests by email; Aikido security researchers found the token grants access across every project the user can reach (not just one project), and GitLab does not verify the sender's email address, so anyone holding the token can act as that user. By changing the target address suffix from '-issue' to '-merge-request' and attaching a patch with target-branch info, an attacker can commit code as the victim; if the patch alters the project's CI/CD config and the user has sufficient permissions, the attacker's jobs run under that user's credentials. The token also bypasses IP restrictions and two-factor authentication. Exploitability depends on the compromised account's role (Guest accounts are minimally exploitable; Maintainer accounts expose protected branches and secrets). As of the report, GitLab cannot disable the feature per-user (only reset the token) and has an open issue to add sender-verification but has not shipped it.
