# Signature verification that treats a non-success outcome (error value, unsupported algorithm) as a pass lets attackers authenticate with invalid tokens

MECHANISM: a cryptographic verification step has more outcomes than 'valid' and 'invalid' (an error return, an algorithm it does not support), and the calling code maps one of those extra outcomes onto acceptance, so an attacker who deliberately triggers that outcome is authenticated without a valid signature.

Two independent 2026 instances, both exploited in the wild:
- A SAML single-sign-on plugin checked the verification result with a loose boolean test, so the library's error return value evaluated as truthy; a deliberately malformed signature was therefore accepted, letting an unauthenticated attacker log in as any account, including administrators. The same plugin also had a separate signature-algorithm-confusion bypass.
- An API gateway accepted JWTs signed with an unsupported algorithm, allowing authentication bypass up to full administrative account takeover.

OPERATIONAL CONSEQUENCE: when reviewing or testing token/assertion validation, exercise the error path and the unsupported-algorithm path explicitly, not only valid and wrongly-signed inputs; a verifier is only as strict as the caller's handling of its least-expected return.

WHAT THIS DOES NOT MEAN: it does not claim the underlying cryptographic primitives or libraries are broken — in the SAML case the library correctly reported an error and the flaw was in how the caller interpreted it. It does not claim these specific flaws remain unpatched; both have fixes, and the exposure is deployments that have not applied them.
