# Two 2026 flaws share a shape: a privilege granted routinely for operations turns out to reach the host operating system

Two separately-disclosed 2026 vulnerabilities instantiate the same mechanism: a privilege that administrators hand out as a matter of ordinary operations — not as a grant of host access — turns out to be sufficient to execute code as the OS user running the service. The exposure comes from the gap between how widely the privilege is granted in practice and what it actually reaches.

CASE 1 — PostgreSQL CVE-2026-6471 (CVSS 7.2, 'PostGREShell'), present since logical decoding was introduced in PostgreSQL 9.4 in 2014. An account holding the REPLICATION attribute can load an arbitrary library as a logical decoding output plugin and run code as the operating-system user running the database server. EXPLOITATION REQUIRES BOTH CONDITIONS TOGETHER: an account carrying the REPLICATION attribute AND a server running with wal_level = logical. The reason it matters is that backup tools, standby servers, change data capture pipelines and monitoring systems routinely hold that attribute. Fixed August 13, 2026 in 18.6, 17.11, 16.15, 15.19 and 14.24, which add an output_plugin_libraries parameter defaulting to 'pgoutput, test_decoding'.

CASE 2 — cPanel CVE-2026-67401, a SQL injection in the EmailTrack feature affecting every supported cPanel/WHM version. An AUTHENTICATED account with mail-related privileges can write files and escalate to root code execution. On shared hosting this crosses the tenant boundary: one account's mail privilege reaches the whole server. Advisory published September 8, 2026.

THE OPERATIONAL READING: when auditing privilege grants, the question is not whether a role sounds administrative but what the code paths reachable from it can load or write. Roles named for a data function (replication, mail tracking) are the ones most likely to be over-granted, precisely because their names do not suggest host access.

WHAT THIS DOES NOT MEAN: two cases are two cases. This does not establish how common the pattern is across software generally, nor that either flaw was exploited — no in-the-wild exploitation is recorded for either. Each case's preconditions above must be carried whenever the pattern is cited; the PostgreSQL flaw in particular is NOT exploitable from a REPLICATION account alone without wal_level = logical.
