# Browser cookie-theft defenses and offense have co-evolved: each at-rest protection pushes attackers further into the live process

Chrome cookie theft shows a clear escalation ladder in which each defensive layer relocates the attack rather than eliminating it, and the current frontier is the running browser process itself.

Sequence: cookie theft via the debugging interface had been discussed since 2018. Google's introduction of App-Bound Encryption (ABE) protected cookies at rest, and Google then observed an increase in attackers using Chrome Remote Debugging to extract cookies instead. Google responded in Chrome 136 by making Chrome ignore the --remote-debugging-port and --remote-debugging-pipe switches when they target the default Chrome data directory unless accompanied by a non-standard --user-data-dir — the non-standard directory uses a different encryption key, which Google says protects Chrome's data from attackers. SpecterOps' technique then bypasses that command-line gate entirely by enabling the Chrome DevTools Protocol from inside an already-running chrome.exe or msedge.exe process: an x64 Beacon Object File (CDP-Enable-BOF) calls the browser's internal StartRemoteDebuggingServer function on a requested port, executing the final call on the browser's UI thread for reliability in the presence of CFG, TLS and CET-sensitive execution. A companion CDP-Toolkit then automates cookie collection via Storage.getCookies — notably without reading the on-disk cookie database, so at-rest encryption is simply not in the path — plus retrieval of history, bookmarks and other browser data.

The generalizable principle: protections that encrypt data at rest or validate launch-time parameters are bypassed by any technique that operates inside the already-authenticated live process, because the process must hold the plaintext to function. Defensive weight therefore has to shift from data-at-rest and command-line controls to process-integrity monitoring — SpecterOps notes defenders can look for process injection targeting chrome.exe and msedge.exe using Sysmon Event IDs 8 and 10 — and to binding sessions to the device so a stolen cookie is not independently replayable.

SCOPE: the in-process technique exploits no Chrome or Edge vulnerability. It assumes the operator already has code execution on the host and sufficient access to manipulate the target process, which places it in a narrower post-compromise scenario than a remotely exploitable browser flaw. It requires a running browser process and is limited to x64 systems. WHAT THIS DOES NOT MEAN: this is not a reason to treat App-Bound Encryption or the Chrome 136 switch restriction as ineffective — each removed a cheaper attack path; it means they should not be counted as protection against an attacker who already has code execution on the endpoint.
