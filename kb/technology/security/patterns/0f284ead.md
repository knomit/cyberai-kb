# Two 2026 resource-exhaustion findings defeat an existing protective limit by growing a quantity the limit does not measure — the cap is real, enforced, and irrelevant

Two independently disclosed 2026 denial-of-service findings share a mechanism that is more specific than 'resource exhaustion': in both, a protective limit IS present and IS enforced, but it measures a DIFFERENT QUANTITY from the one the attacker grows. The limit never fires, not because it was bypassed, but because nothing it counts got large.

CASE 1 — OPENSSL 'HollowByte' (Okta Red Team). An 11-BYTE TLS handshake request causes an unpatched OpenSSL server to RESERVE UP TO 131 KB of memory for a message body THAT NEVER ARRIVES. The root cause is that OpenSSL TRUSTS THE 3-BYTE LENGTH FIELD in the 4-byte handshake header — the declared length is what drives allocation, and the delivered length is never reconciled against it. On the glibc systems Okta tested, that memory is NOT RECLAIMED UNTIL THE PROCESS RESTARTS. OpenSSL shipped the fix on 9 June 2026 with no CVE, no advisory and no changelog entry; fixed releases are 4.0.1, 3.6.3, 3.5.7, 3.4.6 and 3.0.21.

CASE 2 — HTTP/2 BOMB (researcher 'Calif', found using OpenAI Codex). It chains an HPACK compression bomb with a Slowloris-style hold: a zero-byte flow-control window keeps the server from ever freeing any allocated memory. The researcher states the mechanism directly: 'The classic bomb stuffs a large value into the table and references it repeatedly, so servers learned to cap the total decoded header size. Our variant goes the other way: the header is nearly empty, and the amplification comes from THE PER-ENTRY BOOKKEEPING THE SERVER ALLOCATES AROUND IT. THE DECODED-SIZE LIMIT NEVER FIRES BECAUSE THERE'S ALMOST NOTHING TO DECODE.' Affected in default HTTP/2 configuration: NGINX, Apache HTTPD, Microsoft IIS, Envoy, and Cloudflare Pingora. A single client on a 100 Mbps home connection can potentially render a vulnerable server inaccessible within seconds.

THE COMMON SHAPE. In HollowByte the enforced quantity is the DECLARED body length and the growing quantity is RESERVED-BUT-UNFILLED buffer. In HTTP/2 Bomb the enforced quantity is TOTAL DECODED HEADER SIZE and the growing quantity is PER-ENTRY ALLOCATION OVERHEAD. Both limits were added in response to a real earlier attack, and both were left measuring the input the earlier attack inflated rather than the resource the server actually commits.

REVIEW CONSEQUENCE. When auditing a resource limit, the question is not whether a cap exists or what value it holds, but WHETHER THE QUANTITY IT COUNTS IS THE QUANTITY THAT GROWS. A cap on declared or decoded input size does not bound memory committed per unfilled buffer or per bookkeeping entry, and a limit inherited from a previous attack class is the most likely to be measuring the wrong thing.

WHAT THIS DOES NOT MEAN — load-bearing:
- TWO CASES ARE NOT A RATE. This is a shape shared by two contemporaneous findings, not a measured share of 2026 DoS vulnerabilities, and both are single- or double-sourced in this corpus.
- IT DOES NOT CLAIM THE TWO ARE RELATED. Different protocols (TLS handshake versus HTTP/2 HPACK), different researchers, different affected software, no shared infrastructure or attribution. The connection is the mechanism only.
- BOTH ARE DENIAL OF SERVICE, NOT CODE EXECUTION. Neither yields arbitrary code execution or data disclosure, and this record must not be cited as evidence of either.
- SCOPE CONDITIONS MUST TRAVEL: HollowByte's non-reclamation is stated for the glibc systems Okta tested, not universally; HTTP/2 Bomb's affected list is for DEFAULT HTTP/2 configuration on the five named servers, and the 100 Mbps figure is 'potentially' in the source. Historical related CVEs cited alongside HTTP/2 Bomb (CVE-2016-6581, CVE-2025-53020, CVE-2016-8740, CVE-2016-1546) are context, not part of this finding.
