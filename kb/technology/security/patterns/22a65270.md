# Two 2026 flaws with equally public technical detail diverged completely on exploitation, and what differed was precondition breadth, not disclosure

This corpus holds several records in which exploitation followed the publication of technical detail or a proof-of-concept, which invites the rule 'publication leads to exploitation'. Two 2026 cases written up by the same research firm show that rule is not what the evidence supports.

EXPLOITED AT SCALE. 'wp2shell' chains CVE-2026-63030 and CVE-2026-60137 into pre-authenticated RCE in WordPress Core via the REST batch API. Per the record it 'can be exploited anonymously on a STANDARD WORDPRESS INSTALLATION WITH NO PLUGINS OR SPECIAL CONDITIONS REQUIRED', achieving full site compromise. By 18 July 2026 the flaws had CVE IDs, the full mechanism was published and a working PoC was public; mass exploitation began in the early hours of a Saturday UTC, first using public exploit code to exfiltrate hashed credentials, with RCE following as further details emerged.

NOT EXPLOITED. CVE-2026-8037 in Progress Kemp LoadMaster is CVSS 9.8 — HIGHER-RATED — and lets an unauthenticated attacker run commands as root, but only 'VIA A CRAFTED API REQUEST WHEN THE API IS ENABLED'. It was reported via ZDI on 15 April 2026, the advisory published 4 June, and watchTowr Labs published a technical exploit write-up on 29 June. The record states: no in-the-wild exploitation reported.

WHAT DIFFERED: not the severity score, not the availability of technical detail, and not the research firm. The WordPress flaw was reachable on a DEFAULT installation with no configuration precondition; the LoadMaster flaw required a non-default state to be true on the target. Where the vulnerable population is 'everyone running the software', published detail converts into mass exploitation quickly; where it is 'those who enabled a particular feature', the same quality of detail did not.

CONSEQUENCE: a defender ranking work by 'has a PoC dropped?' is using a signal that did not separate these two cases. The signal that did is how much has to be true of a target before the flaw applies — which is knowable from the advisory text and is a property of one's own estate, not of the news cycle.

SCOPE AND CAVEATS: THIS IS TWO CASES, one of them a NEGATIVE observation — 'no in-the-wild exploitation reported' is absence of evidence and could reflect reporting gaps or a shorter observation window, and the LoadMaster write-up is the more recent of the two. The LoadMaster record carries sources: 0 in this corpus. Exposure counts differ enormously between WordPress and a commercial load balancer, so installed-base size is confounded with precondition breadth here and this record cannot separate them. WHAT THIS DOES NOT MEAN: this does NOT claim publishing technical detail is harmless or that disclosure timing is irrelevant — the corpus separately records exploitation beginning within days of details becoming public. It claims only that disclosure is not sufficient, that these two cases differ in precondition breadth, and that precondition breadth is the more actionable of the two variables for someone deciding what to patch first.
