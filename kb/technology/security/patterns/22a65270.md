# Neither published detail nor precondition breadth predicted exploitation across four 2026 flaws; what survives is the size of the exposed population, which this record cannot measure

This corpus holds several records in which exploitation followed the publication of technical detail or a proof-of-concept, which invites the rule 'publication leads to exploitation'. Four 2026 cases show that rule is not what the evidence supports — and the fourth, added later, ALSO BREAKS THE REPLACEMENT RULE THIS RECORD ORIGINALLY PROPOSED.

EXPLOITED AT SCALE, NO PRECONDITION. 'wp2shell' chains CVE-2026-63030 and CVE-2026-60137 into pre-authenticated RCE in WordPress Core via the REST batch API. Per the record it 'can be exploited anonymously on a STANDARD WORDPRESS INSTALLATION WITH NO PLUGINS OR SPECIAL CONDITIONS REQUIRED', achieving full site compromise. By 18 July 2026 the flaws had CVE IDs, the full mechanism was published and a working PoC was public; mass exploitation began in the early hours of a Saturday UTC, first using public exploit code to exfiltrate hashed credentials, with RCE following as further details emerged.

NOT EXPLOITED (AS OF JUNE 2026), PRECONDITION PRESENT. CVE-2026-8037 in Progress Kemp LoadMaster is CVSS 9.8 — HIGHER-RATED — and lets an unauthenticated attacker run commands as root, but only 'VIA A CRAFTED API REQUEST WHEN THE API IS ENABLED'. It was reported via ZDI on 15 April 2026, the advisory published 4 June, and watchTowr Labs published a technical exploit write-up on 29 June. As of that reporting: no in-the-wild exploitation reported.

AUGUST 2026 DEVELOPMENT — THIS CASE MAY NO LONGER HOLD. kb/technology/security/vulnerabilities/network-appliances/d7ae7e85.md records that CISA added A CRITICAL PROGRESS KEMP LOADMASTER FLAW to its Known Exploited Vulnerabilities catalog after roughly 792 exploit attempts (reported August 2026), and kb/technology/security/trends/bb8f5ab8.md carries the same item. CRITICALLY, NEITHER RECORD NAMES THE CVE, so whether the KEV entry is CVE-2026-8037 or a different LoadMaster flaw IS NOT ESTABLISHED IN THIS CORPUS. IF IT IS THE SAME FLAW, the 'not exploited' leg of this case is FALSIFIED. ANYONE RELYING ON THE LOADMASTER NEGATIVE MUST RESOLVE THE CVE IDENTITY FIRST. This is exactly the failure mode this record's own caveat named in advance ('absence of evidence ... could reflect a shorter observation window'), which is why it is recorded here rather than quietly dropped. THE FOURTH CASE BELOW NOW SUPPLIES A NEGATIVE THAT DOES NOT DEPEND ON RESOLVING IT.

THE COMPLICATION — EXPLOITED DESPITE A PRECONDITION. CVE-2026-50522 (CVSS 9.8), a deserialization flaw in Microsoft Office SharePoint Server, 'came under active exploitation AFTER A PUBLIC PROOF-OF-CONCEPT' — and it requires 'a network attacker AUTHENTICATED AS AT LEAST A SITE OWNER'. That is a real precondition, and it did not prevent exploitation. It was the third SharePoint Server flaw from the same July 2026 Patch Tuesday to be exploited.

THE FOURTH CASE — NOT EXPLOITED, AND NO PRECONDITION EITHER. CVE-2026-61511 in vBulletin: SSD Secure Disclosure released a PUBLIC EXPLOIT on 27 July 2026 showing how 'an unauthenticated request can reach PHP's eval() function and execute code WITH NO ACCOUNT OR INTERACTION REQUIRED' (vBulletin 6.2.1 and earlier, 6.1.6 and earlier). vBulletin had patched in late June and shipped 6.2.2 on 1 July, roughly FOUR WEEKS BEFORE the exploit went public. As of 27 July: NO IN-THE-WILD EXPLOITATION CONFIRMED, and the CVE was NOT in CISA's KEV catalog.

WHY THE FOURTH CASE MATTERS MORE THAN THE THIRD. It gives this record a clean negative that is independent of the LoadMaster identity question. But it also DEFEATS THE PRECONDITION READING THIS RECORD WAS ORIGINALLY WRITTEN TO PROPOSE. Compare it directly with wp2shell: BOTH are pre-authenticated RCE requiring no account, no interaction and no special configuration; BOTH had a full public exploit; and their outcomes diverge completely — mass exploitation within hours in one, nothing at four weeks in the other. IDENTICAL PRECONDITION BREADTH, OPPOSITE RESULTS. Precondition breadth cannot be what orders these cases.

WHAT SURVIVES. Only the negative claim, and it is now supported by four cases instead of three: DISCLOSURE ALONE DOES NOT DETERMINE EXPLOITATION. All four had published technical detail, three had public working exploits, and their outcomes and timings differ in every combination — exploited with and without a precondition, unexploited with and without a precondition.

WHAT IS LEFT AS A CANDIDATE, AND WHY THIS RECORD CANNOT TEST IT. The remaining difference between wp2shell and the vBulletin flaw is HOW MANY REACHABLE INSTALLATIONS EXIST: WordPress Core against a declining forum product. That is the confound this record flagged from the outset and still cannot separate — installed-base size was always entangled with precondition breadth, and the fourth case does not disentangle them so much as show that when precondition breadth is HELD EQUAL, the outcomes still diverge, leaving exposure count as the visible remaining variable. The SharePoint lesson is the one durable practical residue: a precondition is not protective in itself, and what matters is HOW MANY REAL TARGETS SATISFY IT. 'The API is enabled' is a deployment choice a minority make; 'someone holds Site Owner' is true in almost every tenant of any size. That quantity is rarely stated in an advisory, which is precisely why the cheap proxies get used instead.

RELATED AND POINTING THE SAME WAY FROM THE OTHER SIDE: kb/technology/security/patterns/7cd2242c.md records August 2026 exploitation of critical enterprise-infrastructure flaws arriving within days of patch, SOMETIMES WITH NO PUBLIC PoC AT ALL. If exploitation can precede or bypass public exploit code entirely, disclosure is neither necessary nor sufficient.

SCOPE AND CAVEATS: THIS IS FOUR CASES, two of them NEGATIVE observations — one now in doubt (LoadMaster) and one bounded by a short window (vBulletin, 'as of 27 July', four weeks after patch and same-day as the exploit release, so a later start remains possible). The LoadMaster record carries sources: 0 in this corpus. Exposure counts differ enormously between WordPress, SharePoint Server, a commercial load balancer and vBulletin, so installed-base size is confounded with precondition breadth throughout and this record cannot separate them; the fourth case narrows but does not close that gap. Confidence is held at its prior value rather than raised: the surviving claim is better supported than before, but it is also a WEAKER claim than the one this record originally made.

WHAT THIS DOES NOT MEAN: this does NOT claim publishing technical detail is harmless or that disclosure timing is irrelevant — the corpus separately records exploitation beginning within days, and in some cases hours, of details becoming public. It does NOT claim preconditions are worthless as a filter, only that breadth of precondition does not order these four cases. It does NOT claim installed base is established as the operative variable — that is the surviving candidate, not a finding. And 'not exploited as of a date' is not 'not exploited': both negatives are observations bounded by their reporting windows.
